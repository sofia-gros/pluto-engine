# PlutoEngine ビルド・配布アーキテクチャ詳細設計

## 1. 概要
PlutoEngineは、Web環境での高度なパフォーマンス（ゼロアロケーション、SoA設計）を維持しつつ、ユーザーが様々な形態でエンジンを導入できるよう、柔軟なビルドおよび配布パイプラインを構築しています。

## 2. 配布形態 (Distribution Methods)
当エンジンは以下の4つの形態で利用可能です。

1. **GitHub上のソースコード (Source Code on GitHub)**
   - コアのカスタマイズやコントリビューションを行う開発者向け。
2. **TypeScript エンジンインポート (TS Engine Imports)**
   - ViteやNext.jsなどのモダンなフロントエンド環境で、型安全性を最大限に活かす方法。
3. **トランスパイル済み JavaScript インポート (Transpiled JS Imports)**
   - バンドラーを使用するが、TypeScriptのコンパイルを省きたいプロジェクト向け。
4. **`<script>` タグによる直接利用 (CDN Ready)**
   - `pluto.global.js` (UMD/IIFE形式) や `pluto.esm.js` (ES Modules形式) をHTMLファイルから直接読み込む方法。

## 3. アグリゲーターパッケージ (`packages/pluto`)
モノレポ構成（`Bun Workspaces`）を採用しているPlutoEngineでは、エンジンを構成する各機能が複数のパッケージに分割される場合があります。これらを単一のエンドポイントとして統合・提供するために、**`packages/pluto`** をアグリゲーターパッケージとして位置づけています。

- **役割**: 各サブパッケージ（コア、レンダラー、数学モジュールなど）のAPIを再エクスポートし、統一されたインターフェース（例: `import { Engine } from 'pluto-engine'`）を提供します。
- **依存解決**: ユーザーは複数のパッケージを個別にインストールする必要がなく、単一のパッケージを導入するだけで完全な機能を利用できます。

## 4. シェーダーのインライン化とスタンドアロン動作
`<script>` タグによるCDN経由の直接利用において、外部ファイル（GLSLシェーダーファイルなど）の非同期読み込みは、初期化遅延やCORSの問題を引き起こす要因となります。

これを解決し、完全にスタンドアロンなブラウザ環境で動作させるため、ビルド時に以下の処理を行います。

- **シェーダーのインライン化**: `tsup`（またはBunのビルドAPI）のプラグイン等を利用し、`.glsl` や `.vert`, `.frag` ファイルの内容をビルド時に文字列としてJavaScriptコード内に直接埋め込みます。
- **単一ファイル提供**: `pluto.global.js` にすべてのアセット情報（シェーダーや小さなデフォルトリソース）がバンドルされるため、ユーザーは1つのスクリプトファイルを読み込むだけでWebGLの描画パイプラインを含むすべての機能を利用開始できます。

## 5. コア設計思想との一貫性
配布ファイルの生成においても、「ゼロアロケーション」「SoA」というコアの掟は遵守されます。インライン化されたシェーダー文字列も初期化時に一度だけコンパイル・パースされ、その後のクリティカルなレンダリングループ内でガベージコレクションを誘発するようなメモリ割り当ては一切行われません。
